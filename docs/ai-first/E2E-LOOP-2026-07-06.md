## Etapa 0 — Leitura do código do loop

Lido `trigger/_shared/loop-tasks.ts`, `trigger/agents/executar-tarefa.ts`,
`trigger/agents/responder-conclusao.ts`, `trigger/agents/revisor.ts`.

Pontos relevantes para o teste com `target_system='nenhum'`:

- `executar-tarefa.ts` exige `INTERNAL_BRIDGE_TOKEN` **incondicionalmente**
  (lança erro antes mesmo de checar `target_system`) — linha 64-66. Path
  `nenhum` não chama o Bridge, mas a env precisa existir mesmo assim.
- `responder-conclusao.ts` resolve `mode` via
  `tenant_agent_config.modo_override` (agente `breno`) → `tenants.modo_padrao`
  → `'humano'`. `cd-demo` foi criado sem `modo_padrao` explícito
  (20260706_001), logo herda o default da coluna: `'hibrido'`. Isso significa
  **draft criado com `status='pending'`, sem auto-envio** — que é exatamente o
  comportamento seguro exigido pela tarefa (nenhum draft aprovado).
- `revisor.ts` para `target_system='nenhum'`: a camada "efeito real"
  (`verificarEfeitoReal`) aprova automaticamente (`confirmed: true, motivo:
  "sem ação externa"`); a camada "grounding" faz 1 chamada LLM real (Kimi via
  Ollama, `_shared/llm-client.ts`) — depende de `OLLAMA_BASE_URL` estar
  acessível a partir do runtime do Trigger.dev cloud.

O agente hardcoded em `responder-conclusao.ts` é sempre `"breno"`
(`agent_name: "breno"`), independente do `agent_id` da `client_task`. O seed
usa `agent_id='breno'` para casar com isso.

Schema de `client_tasks`/`conversations`/`tenant_agent_config`/`tenants`
conferido em `supabase/migrations/00000000000000_baseline.sql` (pós-squash
PR #746 — histórico de migrations anterior a 2026-07-05 foi consolidado nessa
baseline única; por isso as migrations `20260624_003/004` citadas no briefing
não existem mais como arquivos separados, só como schema já embutido na
baseline).

Tenant `cd-demo` (slug) já existe — criado em `20260706_001_homolog_demo_tenants.sql`,
snapshot fictício em `20260706_005_demo_snapshot.sql` (4 lojas, 3 customers,

notificações, `tenant_agents`: `deli`/`cora`/`lara` habilitados — `breno` não

## Etapa 3 — Disparo via API do Trigger.dev — BLOQUEADO

**O que a task pede:** usar o PAT em `~/.trigger-pat.env` para disparar
`agent-executar-tarefa` via API do Trigger.dev (`proj_slexhoelcjwgbopmbzzr`).

**O que foi tentado e o resultado exato (output bruto):**

1. PAT é válido e ativo — confirmado via CLI (usa outro protocolo de auth,
   não a REST API pública):
   ```
   $ TRIGGER_ACCESS_TOKEN=tr_pat_*** npx trigger.dev@4.4.6 whoami
   User ID: cmp1batcm00nzn20joiy2n6m2
   Email:   deli@consultdelivery.com.br
   URL:     https://api.trigger.dev
   ```

2. **A REST API pública de execução rejeita esse mesmo PAT.** Testado direto:
   ```
   $ curl https://api.trigger.dev/api/v1/whoami -H "Authorization: Bearer tr_pat_***"
   HTTP 401 {"error":"Invalid or Missing API key"}

   $ curl -X POST https://api.trigger.dev/api/v1/tasks/agent-executar-tarefa/trigger \
       -H "Authorization: Bearer tr_pat_***" -d '{"payload":{}}'
   HTTP 401 {"error":"Invalid API key"}
   ```

**Causa raiz:** o Trigger.dev v3 separa dois tipos de chave. O **Personal
Access Token** (`tr_pat_...`, o que temos em `~/.trigger-pat.env`) autentica
ações de *gestão* de conta/projeto (CLI: `whoami`, `env list/get`, `deploy`,
`login`) — não tem escopo de ambiente (dev/staging/prod) e por isso a REST
API de execução (`/api/v1/tasks/{id}/trigger`, `/api/v1/runs/{id}`) o rejeita.
Disparar e ler runs exige a **Secret Key do ambiente** (`tr_prod_...`),
que é o valor da env var `TRIGGER_SECRET_KEY` — essa chave **não está** no
arquivo local do PAT; ela vive só no Infisical / env do `bridge-server` na
VPS (`CLAUDE.md` raiz → Infisical: `ANTHROPIC_API_KEY, TRIGGER_SECRET_KEY,
HEYGEN_API_KEY`), inacessível a partir desta sessão (worker Windows, sem
SSH/Infisical configurado aqui).

**Achado positivo (não-bloqueante) — as env vars da task existem em prod:**
usando o PAT para gestão (não execução) foi possível listar as env vars do
projeto:
```
$ TRIGGER_ACCESS_TOKEN=tr_pat_*** npx trigger.dev@4.4.6 env list -e prod
Found 36 environment variables | Project: proj_slexhoelcjwgbopmbzzr | Environment: prod
```
Entre as 36: `BRIDGE_URL`, `INTERNAL_BRIDGE_TOKEN`, `OLLAMA_BASE_URL`,
`LLM_PROVIDER`, `LLM_MODEL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`,
`ANTHROPIC_API_KEY`. Ou seja: **a suposta causa mais comum de falha
("env ausente no Trigger.dev") não se aplica aqui** — o bloqueio é
estritamente de autenticação da chamada de disparo, não de configuração
faltando.

**Não tentado (fora do escopo desta sessão):** obter a `TRIGGER_SECRET_KEY`
via Infisical/VPS para completar o disparo — exigiria acesso a
`172.18.0.3:8080` (Infisical) ou SSH à VPS (`187.127.25.24`), nenhum dos dois
disponível nesta sessão Windows.

## Como destravar (próxima sessão)

Uma das duas:
1. Rodar as mesmas duas chamadas (`agent-executar-tarefa`, depois
   `agent-responder-conclusao`) a partir de uma sessão com acesso a
   `TRIGGER_SECRET_KEY` (prod) — ex.: sessão na VPS, lendo o valor do env do
   `bridge-server` (não expor o valor em log/chat) e usando-o só no header
   `Authorization: Bearer` da chamada REST já documentada acima
   (`POST /api/v1/tasks/{id}/trigger`, `GET /api/v1/runs/{runId}`).
2. Adicionar um endpoint interno no `bridge-server` (auth `x-internal-token`,
   já usado em `loop-despachar.js`) que dispare tasks arbitrárias reusando o
   `TRIGGER_SECRET_KEY` já carregado no processo do Bridge — mais reaproveitável
   para próximos testes E2E, mas é mudança de código nova, fora do escopo
   desta rodada (a task pediu para rodar o E2E existente, não construir
   infra nova).

Depois de aplicada a migration (Etapa 1) e destravado o disparo, a sequência
a rodar é: disparar `agent-executar-tarefa` com
`{"tenant_id": "<cd-demo>", "task_id": "<task da migration>"}` → aguardar →
`SELECT loop_state, execution_result FROM client_tasks WHERE id = '<task_id>'`
→ confirmar `loop_state='done'` (dispara `agent-responder-conclusao`
automaticamente, ver `executar-tarefa.ts` linha 131) → depois
`SELECT execution_result->'revisor', status FROM client_tasks WHERE id='<task_id>'`
+ `SELECT id, status, content FROM agent_drafts WHERE metadata->>'task_id' = '<task_id>'`
para confirmar draft `status='pending'` (nunca aprovar/enviar) +
`SELECT loop_status FROM conversations WHERE id = '<conversation_id>'`.
