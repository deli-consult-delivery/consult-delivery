## Etapa 0 — Leitura do código do loop

Lido `trigger/_shared/loop-tasks.ts`, `trigger/agents/executar-tarefa.ts`,
`trigger/agents/responder-conclusao.ts`, `trigger/agents/revisor.ts`.

Pontos relevantes para o teste com `target_system='nenhum'`:

- `executar-tarefa.ts` exige `INTERNAL_BRIDGE_TOKEN` **incondicionalmente**
  (lança erro antes mesmo de checar `target_system`) — linha 64-66. Path
  `nenhum` não chama o Bridge, mas a env precisa existir mesmo assim.

  `tenant_agent_config.modo_override` (agente `breno`) → `tenants.modo_padrao`
  → `'humano'`. `cd-demo` foi criado sem `modo_padrao` explícito
  (20260706_001), logo herda o default da coluna: `'hibrido'`. Isso significa
  **draft criado com `status='pending'`, sem auto-envio** — que é exatamente o
  comportamento seguro exigido pela tarefa (nenhum draft aprovado).
- `revisor.ts` para `target_system='nenhum'`: a camada "efeito real"
  (`verificarEfeitoReal`) aprova automaticamente (`confirmed: true, motivo:

O agente hardcoded em `responder-conclusao.ts` é sempre `"breno"`
(`agent_name: "breno"`), independente do `agent_id` da `client_task`. O seed
usa `agent_id='breno'` para casar com isso.

Schema de `client_tasks`/`conversations`/`tenant_agent_config`/`tenants`

## Etapa 4 — Rodada 1 — `agent-responder-conclusao` — ❌ FALHOU (bug real de produção)

`agent-executar-tarefa` dispara `agent-responder-conclusao` automaticamente
(`trigger/agents/executar-tarefa.ts:131`) — não precisei disparar manualmente,
o próprio run pai já mostra o filho:

```json
"relatedRuns": { "children": [{
  "id": "run_cmr8xtdxhb4qd0pn8lbreom34",
  "taskIdentifier": "agent-responder-conclusao",
  "status": "FAILED",
  "isFailed": true
}]}
```

**Detalhe do run filho (`GET /api/v3/runs/run_cmr8xtdxhb4qd0pn8lbreom34`):**
```json
{
  "status": "FAILED",
  "payload": {
    "tenant_id": "ecfd0dba-431f-4891-a89d-a1f5f40dde1f",
    "task_id": "fcf8af9b-1571-4a40-bc3b-02d17d2d9939",
    "conversation_id": "3673679c-8047-48e1-9477-357224dbdd6a",
    "triggered_by": "run_cmr8xtc34b17o0pn4r2297bim"
  },
  "error": {
    "name": "ZodError",
    "message": "[{\"validation\":\"uuid\",\"code\":\"invalid_string\",\"message\":\"Invalid uuid\",\"path\":[\"triggered_by\"]}]",
    "stackTrace": "...at run (file:///trigger/agents/responder-conclusao.ts:28:31)..."
  }
}
```

**Causa raiz (bug real, não específico do teste):**
`trigger/agents/executar-tarefa.ts:135` chama
`agentResponderConclusao.trigger({ ..., triggered_by: ctx.run.id })`.
`ctx.run.id` é o ID de run do Trigger.dev, formato `run_xxxxxxxxxxxxx`
(confirmado acima: `run_cmr8xtc34b17o0pn4r2297bim`) — **não é um UUID**.
O `InputSchema` de `trigger/agents/responder-conclusao.ts:8-13` declara
`triggered_by: z.string().uuid().optional()`. `.parse(payload)` na linha 28
do arquivo lança `ZodError` **antes de qualquer leitura/escrita no banco** —
a task morre na primeira linha do `run()`.

Busquei outros chamadores de `agentResponderConclusao.trigger` no repo
(`grep -rn "agentResponderConclusao.trigger" trigger/`) — **só existe esse
um call site**. Ou seja: **100% dos disparos automáticos de
`agent-responder-conclusao` a partir de `agent-executar-tarefa` falham**,
sempre, desde que o campo existe — não é uma condição de borda do teste.

**Consequência real confirmada por SELECT (pós-falha):**
```json
// conversations — segue esperando, o loop nunca fechou:
[{ "id": "3673679c-8047-48e1-9477-357224dbdd6a", "loop_status": "task_pending",
   "active_task_id": "fcf8af9b-1571-4a40-bc3b-02d17d2d9939", "attending_agent_id": "breno" }]

// agent_drafts — nenhum draft criado (revisor nunca rodou, já que o crash é antes disso):
[]
```

**Não é falha do revisor (fail-closed) nem do LLM/Ollama** — a task crasha na
validação Zod do payload de entrada, antes de chegar em qualquer lógica de
negócio (revisor, LLM, Evolution). O gate de segurança "nenhum draft
aprovado sem revisão" nesse caso é cumprido *por acidente* (crash total, não
draft nenhum), não porque o revisor decidiu bloquear.

**Fix aplicado (PR #783, mergeado):** trocado o valor passado em
`executar-tarefa.ts:135` (e no mesmo bug em `breno/responder.ts:316`) de
`ctx.run.id` para `input.triggered_by` — propaga o uuid do usuário/sistema
que originou a cadeia (ou `undefined`, já que o campo é `.optional()`), igual
ao padrão usado em ~30 outros call sites do repo. Ver Rodada 2 abaixo para a
prova de que o fix funciona.
