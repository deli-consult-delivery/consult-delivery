Consult Delivery is a multi tenant platform for food delivery businesses in Brazil, run day to day by a single human founder alongside a growing team of AI agents that handle operations, marketing, customer support, and billing. The platform coordinates work across restaurant stores, an agency layer, and the overall platform itself, and it is currently in the middle of building out a wide feature surface inspired by the EvoNexus product paradigm, reimplemented natively on this stack rather than depending on EvoNexus at runtime.

On the technology side, the frontend is React eighteen with Vite and Tailwind CSS, and the visual design system is anchored to a light themed console style called console dot css, which every new or updated screen should follow. The database is Supabase, which also handles authentication and row level security policies; those policies are described as fully flat and hierarchical across the platform, agency, and store tenancy levels. Background jobs and orchestrated agent workflows run on Trigger dot dev in the cloud, using the official Anthropic SDK rather than the Claude agent SDK, because the agent SDK cannot run inside the Trigger dot dev cloud environment. There is also a Node dot js and Express bridge server running on a VPS under systemd, which talks to WhatsApp through the Evolution API and handles payments through Asaas. Zod is used throughout for validating inputs and outputs, including on every Trigger dot dev task.

The repository is a fairly large monorepo. The main React application lives under source at the root. Trigger dot dev tasks live in a trigger directory, organized by agent and action. The bridge server has its own directory with its own docs. Database migrations live under supabase migrations, timestamped and versioned in git before being applied. There are several small MCP server packages for integrations such as iFood, Asaas, Evolution, and vendor ERP systems, plus a WikiBrain directory used as an accumulated knowledge base and a docs directory that holds architecture diagrams, decisions, and technical debt tracking. A few legacy or exploratory folders exist too, such as an old OpenClaw agent experiment and a handoff bundle from a design tool, which are not part of the live production system.

A few conventions matter a lot here. Nobody commits directly to the main branch, work always happens on a feature branch that gets opened as a pull request. Migrations are additive and reversible by default and can be applied autonomously, but anything destructive, like dropping or truncating real data, requires explicit human approval first. Trigger dot dev tasks follow a fixed pattern, parsing input with a Zod schema, never throwing errors at the top level of a module since that would crash the whole worker, and instead using lazy getters for environment variables. Every table that belongs to a tenant must include a tenant id column with row level security enabled. There is a strict rule against declaring a task finished without showing real, raw output, such as an actual build log, a SQL result, or a test run, rather than just asserting that something should work. The AI agents themselves are named individually, DELI acts as a kind of digital chief operating officer that monitors everything but never messages customers directly, while other agents handle customer relationship management, business intelligence, customer support, collections, sales prospecting, and technical consulting at varying stages of maturity from scaffolded to proof of concept.

As for current focus, the team is in the middle of a structured multi phase rollout that replicates the EvoNexus feature set natively, working through numbered phases with explicit checkpoints that require human approval before moving forward. Recent work has centered on multi tenant row level security correctness, onboarding flows for store owners, an integration and homologation process with the iFood delivery platform, and general platform hardening including quality assurance and technical debt cleanup, with the explicit philosophy that formal partner homologation should wait until the platform is thoroughly robust rather than being rushed.
